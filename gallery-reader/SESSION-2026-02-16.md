## Timeline

### Round 1: Implementation (all 4 tickets)
Read all files, implemented all 4 tickets in order. Build passed clean with zero type errors. Straightforward.

### Round 2: User testing feedback
User reported: "only the exclusivity works" — the input field wasn't reflecting filter state. On app start with `selectedLanguage = 'japanese'`, the input was empty. Selecting a dropdown didn't update the input. Clicking a saved search didn't populate the input correctly.

**Root cause**: The search input was bound to `currentQuery` (free text only), not `fullQuery` (filters + free text). The plan for VERON-62 added `restoreFromQuery()` to parse saved searches into dropdowns, but didn't address the input field needing to show the full query at all times.

### Round 3: Fix — input shows full query
Changed SearchBar.svelte:
- `inputValue` syncs to `fullQuery` instead of `currentQuery`
- Submit uses `restoreFromQuery(inputValue)` to parse input back into dropdowns
- Dropdown `onchange` strips filter tokens from input via `freeText()` helper before searching (prevents double-counting)

Build passed. All 4 features verified working.

## Analysis: Was the back-and-forth avoidable?

**Yes, partially.** The plan for VERON-62 focused on parsing saved searches into dropdowns but didn't consider the reverse direction — the input field should always reflect the full query state. This is an input/state sync issue that should have been caught during planning.

**What would have caught it:**
- Tracing the full data flow during planning: `input ↔ currentQuery ↔ fullQuery ↔ dropdowns`. The plan only addressed `fullQuery → dropdowns` (parsing) but missed `dropdowns → input` (display).
- Asking: "After filters are set, what does the user see in the input field?" — this question would have revealed the gap immediately.
- The plan description even mentioned `fullQuery` causing "doubled filters" but the fix only addressed one direction of the sync.

**Cost of the miss:** One extra round-trip (user test → report → fix → rebuild). Roughly 3 edits that could have been part of the original implementation.

**Takeaway:** When implementing filter/input sync, always trace both directions: state→UI and UI→state. If filters contribute to a query, the input displaying that query must update when filters change, and submitting the input must parse filters back out.
